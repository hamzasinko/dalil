1. Présentation du projet

Dalil (« guide » en arabe) est une bibliothèque Python open source qui rend l'exécution du code compréhensible. Un seul décorateur, @dalil.trace, transforme une fonction en un ensemble d'outils pédagogiques :

  1. un flowchart construit à partir de l'AST ;
  2. une trace d'exécution ligne par ligne (variables, branches, retours) ;
  3. une estimation de complexité temporelle et spatiale ;
  4. un rapport HTML autonome ;
  5. un export LaTeX au format algorithm2e / algorithmicx.

État actuel

La version 0.1.0 est un squelette : l'API publique et les modèles de données existent, les couches métier lèvent encore NotImplementedError. Ces comportements sont couverts par des tests xfail(strict=True), ce qui garantit qu'ils seront implémentés sans oublier les tests.

3. Installation et environnement

Prérequis

  • Python 3.9 ou plus récent (3.13 recommandé pour le développement) ;
  • Git et, si possible, GitHub CLI (gh) ;
  • aucun service externe n'est requis pour les tests.

Mise en place

git clone https://github.com/hamzasinko/dalil.git
cd dalil

python -m venv .venv
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
# Linux / macOS
source .venv/bin/activate

python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
pre-commit install

Sous Windows, si PowerShell bloque l'activation du venv, exécutez une fois : Set-ExecutionPolicy -Scope CurrentUser RemoteSigned.
L'installation est éditable : toute modification dans src/dalil/ est immédiatement visible, sans réinstallation.

Cycle de travail type

# 1. Se placer sur dev et récupérer les dernières modifications
git switch dev
git pull --ff-only

# 2. Créer la branche de travail
git switch -c feature/tracer-core

# 3. Coder + tester
python -m pytest
python -m ruff check .
python -m ruff format --check .
python -m mypy --strict src tests

# 4. Commiter (Conventional Commits)
git add -A
git commit -m "feat(tracer): record locals on each line event"

# 5. Pousser et ouvrir la PR vers dev
git push -u origin feature/tracer-core
gh pr create --base dev --fill

# 6. Après validation et CI verte : squash merge
gh pr merge --squash --delete-branch

Règle d'or : le comportement et la valeur de retour d'une fonction décorée ne doivent jamais changer. Toute fonctionnalité doit être accompagnée de tests nominaux et de cas limites.

6. Workflow GitHub

Protection des branches

Les branches main, dev et prod exigent :

  • une pull request (pas de push direct) ;
  • 1 revue approuvée (les reviews obsolètes sont réinitialisées) ;
  • les checks requis lint, test et build ;
  • un historique linéaire (squash ou rebase uniquement) ;
  • aucun force-push ni suppression de branche ;
  • la résolution des conversations avant merge.
Compte solo : GitHub interdit d'approuver sa propre PR. Comme enforce_admins est désactivé, le mainteneur peut merger via le bypass administrateur (gh pr merge --squash --admin). Dès qu'un second mainteneur est ajouté, activez enforce_admins et exigez une vraie revue.
Sur un dépôt personnel, GitHub refuse les restrictions de merge par utilisateur/équipe sur prod (erreur 422). Seuls les collaborateurs avec accès en écriture peuvent merger. Pour une restriction explicite, transférez le dépôt vers une organisation.

7. Publier une version

Prérequis unique : PyPI Trusted Publishing

Le workflow de release utilise OIDC : aucun token PyPI n'est stocké dans GitHub. Il faut déclarer le publisher une seule fois sur PyPI :

  1. Se connecter sur pypi.org puis ouvrir Account settings → Publishing.
  2. Créer un pending publisher avec : propriétaire hamzasinko, dépôt dalil, workflow release.yml, environnement pypi.
  3. Créer l'environnement pypi dans Settings → Environments du dépôt (protection par approbation recommandée).
Tant que ce publisher n'existe pas, tout déclenchement de release.yml échoue au job Publish. C'est la raison pour laquelle prod n'a pas encore été avancée.

Procédure de release

  1. Mettre à jour __version__ dans src/dalil/__init__.py et CHANGELOG.md.
  2. Merger dev → main via PR.
  3. Merger main → prod via PR : le push déclenche release.yml.
  4. Le workflow teste, construit, publie sur PyPI, puis crée la release GitHub avec les notes générées.

Alternative : pousser un tag v0.2.0 déclenche le même workflow.

Ordre des opérations

feature/* --PR--> dev --PR--> main --PR--> prod --CI/CD--> PyPI + GitHub Release

Critères d'acceptation par phase

0.2.0 - Flowchart

  • un nœud d'entrée et de sortie unique pour toute fonction ;
  • les branches if/elif/else, boucles for/while et return produisent des arêtes correctes ;
  • les sorties DOT et Mermaid sont déterministes (tri stable) ;
  • cas limites : fonction vide, pass, try/except, lambdas ;
  • tests de propriété Hypothesis sur le nombre d'arêtes et la connexité.

0.3.0 - Tracer

  • aucune modification du comportement, de la valeur de retour ni des exceptions ;
  • sys.settrace restauré même en cas d'exception ou de thread ;
  • historique limité en mémoire (option de taille maximale) ;
  • cas limites : récursion, générateurs, async, décorateurs empilés.

0.4.0 - Complexité et LaTeX

  • notation O(...) justifiée par la structure détectée ;
  • sortie LaTeX compilable avec algorithm2e et algorithmicx ;
  • échappement correct des identifiants et des chaînes.

0.5.0 - Rapport et CLI

  • HTML autonome (CSS inline, aucune ressource réseau) ;
  • échappement systématique des valeurs utilisateur (XSS) ;
  • CLI testée avec capsys et codes de sortie stables.

1.0.0

  • couverture ≥ 90 % maintenue, documentation publiée, API gelée ;
  • publication PyPI via Trusted Publishing et notes de release automatiques.

9. Checklist et dépannage

Checklist avant chaque pull request

  • branche créée depuis dev et PR ciblant dev ;
  • titre de PR au format Conventional Commits ;
  • tests nominaux et cas limites ajoutés ;
  • python -m pytest vert avec couverture ≥ 90 % ;
  • ruff check, ruff format --check et mypy --strict src tests verts ;
  • documentation et CHANGELOG.md mis à jour ;
  • template de PR rempli, issue liée (Closes #123) ;
  • CI verte sur les 15 combinaisons + lint + build.
